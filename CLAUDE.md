# Puzzle

Open-source (GPL-3.0-or-later) FEM/CFD pre- and post-processor: one solver-neutral model run on CalculiX, Elmer, Code_Aster, FEniCSx, Code_Saturne and OpenFOAM, aiming for Ansys/COMSOL usability. An overarching principle: users can be abstracted from the mechanics if they want, so non-experts can rely on a built-in expert (the agent) to set up, check and explain, while experts keep every detail; so every feature has a plain, intent-level way in and is reachable and explainable by the agent (MCP, skills), never GUI-only. Decisions live in `docs/adr/` (read the index before changing architecture); the shareable design doc is a Claude Doc: https://claude.ai/code/artifact/7e7a31c7-a7a6-49b3-97ed-05307493943f. Keep both in sync when a decision changes.

## Workflow

- Work on the `development` branch. Push to `main` only when the maintainer says so.
- Contributors are the maintainer and Claude; no CLA/DCO.
- Commit and push only when asked.
- New architectural decision → new ADR from `docs/adr/template.md`, plus a row in `docs/adr/README.md`.
- Finishing an ADR an agent will use includes its agent skill (ADR 0057): add or update `src/puzzle/agent/skills/<name>.md` (when to read it, the steps, tools and arguments, units, mistakes), add missing MCP tools it needs, and list the ADR in `WITH_SKILLS` in `tests/test_agent_skills.py`.

## Commands

Environments come from pixi (`pixi.toml`, ADR 0013). Each native solver has its own environment.

```sh
pixi run -e dev check          # ruff lint + format check + all tests incl. native CalculiX runs
pixi run -e dev pytest -k name # one test
pixi install -e fenicsx        # other native solvers: fenicsx, code-aster (linux-64/win-64)
pixi install -e mmg            # MMG for anisotropic mesh adaptation (ADR 0066; not osx-arm64)
pixi run -e dev build-calculix   # CalculiX with MKL PARDISO (ADR 0051; linux-64, osx-64, win-64), used before conda-forge's
pixi run -e dev puzzle solvers [--build]       # each solver and how it runs here; PARDISO's build (ADR 0068 step 4)
pixi run -e dev import-materials "<path>/Materials_Hunt_List.xlsx"
pixi run -e dev puzzle gui examples/cantilever   # the desktop GUI
pixi run -e dev puzzle agent-key set            # store the Claude key in the keychain (hidden prompt)
pixi run -e dev puzzle ask PROJECT "question"    # the built-in agent in a terminal
pixi run -e dev puzzle agent pick [--use]       # measure local models, recommend one (ADR 0022)
pixi run -e dev puzzle progress PROJECT --study NAME [--plot p.png]  # how a run converged (ADR 0054)
pixi run -e dev puzzle log PROJECT --study NAME [--problems] [--grep RE] [--context N]  # a run's whole solver logs
pixi run -e dev puzzle contacts PROJECT [COMPONENT] [--solver S]     # each contact's setup and initial state (ADR 0056)
pixi run -e dev puzzle schematic PROJECT [--svg F] [--json]          # the project as nodes and wires (ADR 0058)
pixi run -e dev puzzle operators PROJECT [NAME] [--json] [--export]  # operators' values; write exports (ADR 0062)
pixi run -e dev puzzle optimise PROJECT NAME [--points] [--budget N] [--apply]  # design of experiments (ADR 0063)
pixi run -e dev puzzle convergence PROJECT STUDY [--levels N] [--ratio R] [--points]  # mesh convergence, GCI (ADR 0066)
pixi run -e dev puzzle error-estimate PROJECT STUDY [--field F] [--json]  # a run's ZZ error, where it is largest
pixi run -e dev puzzle adapt PROJECT STUDY [--target T] [--budget N]       # adaptive refinement passes
pixi run -e dev puzzle hosts add lab --address lab.example [--scheduler slurm]  # remote hosts (ADR 0021)
pixi run -e dev puzzle run PROJECT --study NAME --host lab                     # solve there once
pixi run -e dev puzzle run PROJECT --all          # every study, one after another (ADR 0073; or --study twice)
pixi run -e dev puzzle jobs PROJECT [--live] [--resume all] [--cancel JOB]       # solves held by the job runner (ADR 0067)
pixi install -e runner                          # PSI/J for the job runner's schedulers (ADR 0067)
pixi run -e packaging build-packages            # Puzzle's conda packages into packaging/output (ADR 0068)
pixi run -e packaging make-installer --build    # the installer from pixi.lock; smoke-test it with scripts/smoke_installer.py
```

A plain `.venv` also works (`pip install -e ".[dev]"`); set `PUZZLE_SOLVER_PATH=$PWD/.pixi/envs/calculix/bin` so solver tests find `ccx`. Started from a pixi env without `pixi run` (the env's own `puzzle`, an editor's Python, an MCP client), Puzzle still finds the solver envs beside its own (`jobs.runtime.pixi_solver_dirs`), after PUZZLE_SOLVER_PATH and PATH. Docker and Podman are found off PATH too, where their installers put them (`ENGINE_DIRS`, e.g. Docker Desktop's app folder on macOS), and that folder goes on the engine's PATH.

CI (`.github/workflows/ci.yml`): pushes to `development` run Linux and Windows; pushes to `main` and pull requests into it add both Macs (macOS minutes cost ten times Linux's); Actions → CI → Run workflow takes the machines (a JSON list) and pytest arguments, for checking a fix on one platform cheaply. GitHub's Linux and Windows machines have 16 GB and no GPU, Windows' FEniCSx has no PETSc (`tests/solvers.py` `needs_petsc`), and a test failing only because an optional package isn't installed is skipped (`tests/conftest.py` `OPTIONAL`, for the pip job).

Dynamics (ADR 0041): a `transient` step solving solid mechanics is structural dynamics (Newmark, `time_step`/`end_time`, `method` direct or modal, `hht_alpha`), a `frequency_domain` one harmonic response (`frequencies` as text, or start/end/points/spacing); Rayleigh `rayleigh_alpha`/`rayleigh_beta` per study (`common.rayleigh`; Code_Aster's AMOR_ALPHA is the stiffness one), `damping_ratio` with the modal method only; CalculiX `*DYNAMIC, DIRECT, ALPHA=0` or a stored `*FREQUENCY` step then `*MODAL DYNAMIC`/`*STEADY STATE DYNAMICS` (one step per listed frequency), Code_Aster `DYNA_NON_LINE` and `DYNA_VIBRA` HARM PHYS (complex parts written as two real results); FEniCSx (`study.py` `solve_transient`/`solve_harmonic`: matrices once, SciPy LU, held dofs eliminated, consistent initial acceleration) and Elmer (StressSolve, Bossak alpha 0, Rayleigh in the Material; harmonic as a `Scanning` run, one frequency per scan, `Eigen Vector Component = "complex"`; it starts from zero acceleration, so a sudden load lags early) solve directly (modal refused; HHT refused on Elmer); harmonic results are `displacement_amplitude`, `displacement_phase` and `displacement` at the peak instant (`common.harmonic_fields`); force and pressure may follow an amplitude; every CalculiX `*STEP` is tagged `** puzzle step k` (0 = helper) and results are mapped back by `inp.step_owners`; benchmarks in `tests/integration/test_dynamics.py`. Buckling (ADR 0028): a `buckling` step (settings `modes`, `preload` = hold the static step just before it, `shift` on Code_Aster only) on CalculiX (`*BUCKLE`; with a preload the static step gets NLGEOM and the buckle step PERTURBATION; the reader drops each buckle step's static block and numbers modes) and Code_Aster (`RIGI_GEOM` + `CALC_MODES` `MODE_FLAMB`, `CHAR_CRIT` = load factor; `run_study` hands a preloaded buckling step its static step); results are one step per mode, value = load factor, labelled by `StepResult.label()`; benchmarks in `tests/integration/test_buckling.py`. Body loads (ADR 0037): `gravity`, `acceleration` (inertia −a) and `rotation` (centrifugal) on a body selection, on CalculiX, Code_Aster, Elmer and FEniCSx (`adapters.common.body_load`), benchmarked in `tests/integration/test_body_loads.py`; they make density required. Remote loads: `remote_force` (an RBE3-equivalent traction, `adapters.common.remote_load`, integrated on the curved faces) and `remote_displacement` (a rigid motion field) on all four FE solvers, `remote_force_rigid` on CalculiX (`*RIGID BODY`, extra nodes past the mesh's ids) and Code_Aster (`LIAISON_SOLIDE`); torsion benchmarks in `tests/integration/test_remote_loads.py`. Beams (ADR 0027): a `polyline` geometry step meshes into line elements (`Mesh.beam_blocks()`: line blocks of line-body parts; a solid's mesh also has line blocks on named edges, which are not elements); `Component.beam_sections` gives each line part a section; CalculiX B31/B32 (`OUTPUT=2D` maps expanded results back) and Code_Aster POU_D_T (order 1 only; `beam_forces` field), refused on Elmer and FEniCSx (`Capabilities.beams`); `tests/integration/test_beams.py`. Shells (ADR 0027): `sheet`/`curved_sheet` geometry steps mesh into triangles (`Mesh.shell_blocks()`); `Component.shell_sections` gives a thickness and offset; CalculiX S6/S8 (S3 refused: it locks; shell pressure written as −p, since its P pushes along the element normal) and Code_Aster DKT (order 1 only; `FORCE_COQUE`); a positive pressure on a sheet pushes against the face's normal; `tests/integration/test_shells.py`. An `Amplitude` (factor against time) on a feature (`Feature.amplitude`) varies it in transient steps; only heat flux so far (`Capabilities.amplitude_features`), refused elsewhere. Transient steps take `time_step` and `end_time` settings, and `time_scheme` (default `backward_euler` on every solver, so shoot-outs compare like with like; also `crank_nicolson`, `bdf2`, `theta` with a `theta` setting, where the capability matrix's `time_schemes` allows); heat physics takes `initial_temperature`. Heat transfer uses a material's temperature tables (conductivity, specific heat, density) by default, which makes it nonlinear; the physics setting `temperature_dependent_materials = false` uses the single values instead (closed-form benchmarks do this). `tests/integration/test_nonlinear_conduction.py` checks the tables against the Kirchhoff solution (all four FE solvers within 0.002 K) and in a transient shoot-out. Results come back as one step per output time (`StepResult.value` = time). Whole-model values (e.g. stored electric energy) are fields with `location="global"`. Magnetodynamics (ADR 0047, stage 1): a `frequency_domain` step in magnetic fields is time-harmonic A–V on Elmer (`elmer/magnetics.py`: Scanning, `Angular Frequency` per scan, BiCGStab because UMFPACK fails on it; a massive `coil_current` gets I/area on its start face and V = 0 on its end; a `stranded_coil` runs CoilSolver as its own Component with `Coil Type`, or windings are scaled together, `Use Unity Conductivity`, field × −N I, σ = 0 in its body) and FEniCSx (`solve_magnetodynamics`: A and V in real/imaginary blocks, V in every conductor); `adapters/eddy.py` pairs coils with terminals by nodes and computes `loss_density`, `joule_loss` (total and per body), `magnetic_energy` (¼∫B·H*), `coil_resistance`/`coil_inductance` (voltage over current) from element values on both; static windings take the same path. `puzzle/magnetics.py`: skin-depth warnings (recipe size vs δ/2, then the elements meshed, the air region at a solve's start), `skin_refinement` (refine-near δ/3). `heat_generation` (W/m³ on bodies) on the four FE solvers; a `loss_density` transfer becomes one on its `target_selection` with the total kept (`transfer.heat_from_losses`). Stage 2: transients (Elmer backward Euler only, its BDF2 measured wrong; FEniCSx BE or BDF2, factored once by `study.Factored`), `lorentz_force_density` → a structural `body_force` (`transfer.forces_from_lorentz`; transferred fields made linear per element, totals over curved elements), axisymmetric A_φ (windings and passive conductors; Puzzle derives B, J and the rest, `eddy.axisymmetric_fields`; FEniCSx's curl form; regions as separate bonded parts, since one geometry's face steps fuse). Closed windings (no terminals) circulate about `eddy.coil_axis` (largest principal moment) on both solvers; a winding's current is uniform along its turns (Elmer `Normalize Coil Current` with Coil Type stranded; FEniCSx unit direction, divergence cleaned in the coil, divided by the current it carries); solid rings in 2D by superposition (`eddy.combine_axisymmetric`: a basis per ring's unit voltage, Elmer as scans, FEniCSx one factorisation); Elmer 3D magnetics run on MPI with Settings > Solvers > Parallel processes per run (`ElmerAdapter.processes`, `run-mpi.sh`: ElmerGrid METIS + `mpirun ElmerSolver_mpi`; the reader merges partitions by position); history mode `separate` keeps touching 2D faces as regions. Benchmarks `tests/integration/test_eddy_currents.py`, `test_eddy_axisymmetric.py` (billet, solid tube, sphere), `test_closed_coil.py`, `test_team7.py` (TEAM 7 within 2.2 % RMS), `test_heat_generation.py`.

2D models (ADR 0048): `Component.dimension` 2d_planar (`planar_model` plane_stress, its thickness from a part's thickness section, or plane_strain) or 2d_axisymmetric (Y the axis, X the radius); parts are faces at z = 0 (history `face` from a profile, sides named by the sketch; `section` of another geometry, edges named by the 3D faces they cut), meshed in 2D (`Mesh.planar`: faces are regions, not shells; `region_blocks()`; "hexahedra" is quadrilaterals there, all of them by default: `MeshRecipe.quadrilaterals` all meshes at twice the size and subdivides, transfinite counts halved, or mixed recombines only); edge forces spread over `common.load_area` (an axisymmetric force is the whole revolution's); CalculiX CPS/CPE/CAX (heat on CPS and DCAX: no DC2D), Code_Aster C_PLAN/D_PLAN/AXIS (pressure edges ORIE_PEAU'd), Elmer Cartesian 2D/Axi Symmetric with `Plane Stress`, FEniCSx gdim 2 with thickness or 2πr weights; stress stored as 6 components (zz the hoop); benchmarks in `tests/integration/test_planar_benchmarks.py`. Rounds 2–5: `geometry/planar.py` (rectangle, circle, annulus, polygon, slot, `offset` a wall along a line, sides named; a flat part's fillet/chamfer rounds corners; import `flat` lays flat faces on XY; DXF regions share edges; `test_planar_shapes.py`); the mesher turns clockwise 2D entities round (`generate._counter_clockwise`: CalculiX refused reversed elements); axisymmetric results draw revolved (`post/revolve.py`, Settings > Results; the store keeps no dimension, so `revolve.mark_dimension(mesh, component)` a stored mesh); 2D totals are the whole part's (Code_Aster's AXIS reactions were per radian and C_PLAN per thickness, scaled by its reader; `probes.totals_basis`; `test_planar_totals.py`); 2D dynamics, body loads and temperature loads on all four FE solvers (`test_planar_dynamics.py`; CalculiX drops point loads on 2D elements in steps over modes, so `inp._as_edge_pressure`; Elmer's plane strain omits the out-of-plane thermal strain, so α(1+ν) is written and σz corrected); planar magnetics A_z on Elmer and FEniCSx through `eddy`'s 2D path (`planar`, totals per metre; `test_eddy_planar.py`); 2D CFD on OpenFOAM and Code_Saturne as the 2D mesh extruded one cell thick in the adapter (`mesh/layer.py`: empty/wedge or symmetry, cells keep their 2D element's id, `layer.match` by nearest centre; Code_Saturne time-marches a wedge at 0.5 h/U; `test_cfd_2d.py`). Solver tests in `tests/integration/` skip when the solver isn't available; `tests/solvers.py` `over("elmer", "fenicsx")` parametrizes a test over solvers. Rendering tests run only with `PUZZLE_RENDER_TESTS=1`; check renders by looking at the PNG (`puzzle show ... --screenshot`). Container runs: `PUZZLE_RUNTIME=docker pytest tests/integration` after building images in `containers/`.

## Conventions

- Everything is SI internally (m, kg, s, N, Pa, K). Imported geometry is converted to metres; `Quantity.to_si()` converts user values. Never pass units implicitly to a solver.
- Adapters only claim a capability once a benchmark for it passes. Elmer's mechanical contact is conformal bonding only (shared nodes; a mortar tie isn't written, so nonconformal bonds are refused and unclaimed); its slide/friction/stick are `experimental`.
- Tests compare against closed-form or published answers with stated tolerances, not snapshots.
- Match the surrounding code: dataclasses/Pydantic, type hints, short docstrings that say why.
- **Adapters take transferred fields as `inputs`** (`write_input(..., inputs)`); one that can't apply an input must refuse it (`base.refuse_inputs`), never ignore it. Temperature loads (role `load`) work on CalculiX (`*TEMPERATURE` per step, initial temperature = reference), FEniCSx (thermal strain in the weak form), Code_Aster (field built in the .comm from `transferred-temperature.txt`, matched by coordinates, `AFFE_VARC`) and Elmer (an ASCII restart file `puzzle-temperature.result` in Elmer node order). Prestress (role `prestress`, CalculiX): the static source study on the same component is replayed as an NLGEOM first step and the study's own steps become `PERTURBATION` steps; a `.prestress` marker tells the reader to drop the replayed step's results (`test_prestress.py` matches a 1D beam with geometric stiffness to 0.1%). the reference is the structural physics' `reference_temperature` (default 20 °C). `tests/integration/test_transfers.py` checks thermal bending across solver pairs and an interpolated mesh.
- **Multi-step studies:** CalculiX writes every solve step in one deck; adapters with `max_solve_steps = 1` (Elmer, Code_Aster, FEniCSx, Code_Saturne) get the study split by `run_study`, one job per step on the same mesh. Those steps are independent analyses; sequencing state from one step to the next is what transfers are for.
- **The GUI shows names, never ids or internal keys.** Anything with a fixed set of values is a dropdown of readable names that stores the real value: `gui/choices.py` (`choices(project, obj, path)`, `label`, `solver_label`) drives the properties panel; menus, `window.choose` (takes (name, value) pairs), the tree, history lines, Problems, the agent panel and the results bar use the same labels. Quantities' units are checked when typed (`units.known`). New GUI elements follow this. Selections are edited from picks through `window.edit_selection(geo, index, mode)` (replace, add, remove; the tree's and the Geometry tab's Selections list's right-click, Edit in the view). Creating something asks everything in one dialog (`window.ask_form`, `gui/quick_form.py`; tests fill it with `tests/forms.py` `fill`), never a chain of popups. Long forms use `gui/form.py` `FormPanel` (ADR 0036): sections, label | field | unit rows, descriptions from `DESCRIPTIONS`, the blocking message on top. Never name a widget attribute after a QWidget method (`height`, `width`, `size`, `font`). Colours come from the theme (ADR 0045): `theme.role(label, "muted")` or palette colours in a style sheet, never a hex code inline. `tests/test_gui_names.py` checks every tree item's properties for ids, `null`, "N items" and snake_case keys (ADR 0029); panels that belong to one context (the results bar, the ribbon) show through `MainWindow.set_context`, and mode-specific fields hide through `APPLIES` in `gui/properties.py`.
- **Display units (ADR 0024):** values are stored as typed (and converted to SI for solvers); what the GUI shows follows Settings → Units (default SI: a 2.5 mm size shows as 0.0025 m; a bare number typed is in the unit shown). Use `units.shown`/`pretty` and `settings.length_unit()` in new GUI code, never a hard-coded mm. Preferences never change results. A project may switch on its own system (ADR 0030, the `ProjectUnits` object, kind `units`); `settings.use_project` applies it on refresh, so `current().display_units()` is always what's shown; tests reset it in `conftest._fresh_settings`.
- **Solver settings (ADR 0023):** shared ones (`adapters.settings.SHARED`) live on each solve step; each solver's own in `Study.solver_settings[solver]` from its `settings_schema()`, pass-through in `Study.expert_settings[solver]` (checked by `check_expert`, placed or refused, never dropped); run keys cover only the running solver's blocks; write only what is set so defaults never move results. CalculiX applies them per written step (`inp.with_settings`), Code_Aster as keyword overrides on the .comm (`code_aster/expert.py`), Elmer as SIF section overrides (`elmer/sif_edit.py`), FEniCSx through `case.json` settings and PETSc options, Code_Saturne through its case model and setup.xml paths, OpenFOAM through `foamDictionary` in `Allrun`; `Capabilities.shared_settings` says which shared ones each takes (others refused). Presets are `SettingsPreset` (kind `preset`).
- **Every project change goes through `puzzle.commands.Session`** (CLI, GUI, scripts, agents); no client writes project files itself. New user actions become commands in `commands/model.py`. Errors a client can act on are `PuzzleError` with a code from `puzzle.errors.CODES`.

## Gotchas

- **Gmsh is global state.** Always use `puzzle.geometry.gmsh_session()`; it holds a lock and sets OCC import units to metres. Don't nest sessions.
- **OpenCASCADE is serialised:** `geometry.session.occ_lock` (re-entrant) wraps `regenerate`, `read_cad`, `write_brep`, `resolve_geometry`, `check_geometry`, and every Gmsh session takes it before its own lock. Gmsh and OCP share one OCCT; concurrent GUI jobs (a preview and a selection check) failed inside it (`NCollection_IndexedMap::FindKey`, bodies lost while placing). New OCC work off the GUI thread must take it too.
- **OCC pads bounding boxes** by ~1e-7 m. Plane tests need a tolerance of at least 1 µm.
- **Entity names** (`face-3`) follow STEP file order; signatures (kind, measure, centre) re-find them after placement or fragmenting.
- **Element node order:** Gmsh differs from CalculiX, Elmer and VTK for tet10 (last two edge nodes swap). Adapters own the reordering; shared face lookups live in `adapters/common.py`.
- **Custom PDE weak forms** are evaluated with `eval` and no builtins in `study.py` (`UFL_NAMES` plus the unknown, `v_<u>`, `<u>_n`, `dt`, coefficients, `x`, `dx`/`ds` taking selection names, `prop(...)`). That limits mistakes, not a determined attacker, so equations (and script operators) run only in a trusted project (`puzzle.trust`, ADR 0062 phase 4). dolfinx wants each cell tagged once, so the case mesh tags volumes by material selections (or parts) only.
- **FEniCSx `study.py`** runs inside the FEniCSx env and must not import puzzle. dolfinx 0.11 `LinearProblem` needs `petsc_options_prefix`; MUMPS is used only if PETSc has it. Windows dolfinx has no PETSc, so `study.py` falls back to SciPy (ARPACK; CG for the stress projection), its real systems factored by MKL PARDISO through pypardiso where installed (win-64's fenicsx env; `_spsolve`, `_Factor`) and SuperLU otherwise and for complex ones; `PUZZLE_FENICSX_BACKEND=scipy` forces that path, `PUZZLE_FENICSX_LU=superlu` SuperLU (LE1 natively on Windows: 9.8 s PARDISO, 30.8 s SuperLU).
- **Code_Saturne specifics:** an imposed wall flux is positive leaving the fluid (the adapter flips Puzzle's sign); turbulent intensity is in percent; the steady algorithm takes thousands of iterations for conduction-dominated scalars (use `pseudo_time_step`). RANS wall functions under-predict friction ~15% at Re_tau ~ 400; benchmark them at Re ≥ 1e5.
- **OpenFOAM's `etc/bashrc`** reads the positional arguments it is sourced with (it can source files named there), so the image's entrypoint clears them first. Its pressure is kinematic (p/ρ); the adapter writes and reads Pa. `scalarTransport` is not under-relaxed and sits in `residualControl`, or simpleFoam stops when only the flow has converged.
- **Code_Saturne's Gmsh reader** names groups by physical tag number, not name: zones select `"2"`, not `"Inlet"` (`write_med` returns the tags). Results are per cell (`location="element"`), matched to Puzzle elements by node-average centres (`match_points`, float32-tolerant).
- **Temperature tables per solver:** CalculiX `*CONDUCTIVITY` value/temperature lines plus tight `*CONTROLS, PARAMETERS=FIELD` (its defaults stop 0.2 K short); Elmer `Variable Temperature` tables with nonlinear iterations; Code_Aster `THER_NL` (LAMBDA and enthalpy BETA functions) with `THER_NON_LINE`, steady via `ETAT_INIT=_F(STAT='OUI')`; FEniCSx a closed-form piecewise-linear UFL expression and Picard iteration. Code_Aster is written with `PARM_THETA` (1.0 by default, not its own 0.57). With temperature tables Code_Aster steps the enthalpy, the others rho cp(T); they differ by O(dt) (0.7 K at dt = 5 s in the shoot-out, 0.15 K at 1 s), Code_Aster being closer to the converged answer.
- **Time schemes at t = 0:** backward Euler agrees across all four solvers to 3 decimals and BDF2 between Elmer and FEniCSx. For theta < 1 the starting state matters: Code_Aster and FEniCSx start from the given initial field, while Elmer appears to apply the boundary values to the starting state first, and its Crank-Nicolson damps the initial jump (plain CN from a stepped start oscillates: 18.7 K in a FEniCSx experiment). So theta-scheme results differ between Elmer and the other two after a sudden load; prefer backward Euler or BDF2 there.
- **Code_Aster 18** needs `INCREMENT` even for steady `THER_LINEAIRE`; table numbers need `FORMAT_R` (default keeps 5 digits). Containers run as your uid with `HOME=/tmp` (run_aster needs a home).
- **Elmer output** lands in the mesh directory (`mesh/case_t0001.vtu`). Points come in Elmer node order (no point ids); `GeometryIds` there is cell data. Eigenvalues (omega^2) are parsed from the solver log.
- **CalculiX `.frd`** is fixed width (values can touch); match record tags on the first token. Modal block values are frequencies in Hz.
- **Native solver runs** must look activated: `NativeRuntime.environment()` puts the conda/pixi env on PATH and sets `CONDA_PREFIX` (Windows otherwise fails with 0xC0000135). Elmer from conda also needs `ELMER_HOME` = env prefix.
- **Elmer image** is built without MUMPS (Debian trixie lacks ParMETIS).
- **Elmer magnetics:** the A-V edge system stalls under GCR/BiCGStab here, so it is solved directly (Elmer then tree-gauges it). Unlisted SIF keywords such as `Use Magnetic Norm` need an explicit type (`Logical True`), or parsing fails. Lowest-order edge elements give B constant per element; nodal B is an average, so check it away from material interfaces and use the stored energy for the whole field.
- **Local mesh sizes** are Gmsh `Constant` fields over the selection's entities (min-combined background field); point sizes alone barely refine curved bodies.
- **Contacts:** adapters must refuse contacts they don't write (`common.check_contacts`, code `unsupported`); conformal bonds need nothing (shared nodes). Nonconformal bonds: CalculiX `*TIE` (source = slave surface, target = master; works for heat too), Code_Aster `LIAISON_MAIL` (source face into the target part's volume; structural only). `tests/integration/test_contact.py` uses `conftest_geometry.split_bar_project`. Don't put SPCs on CalculiX tie slave nodes: the conflict floods the log with cascade warnings. Frictionless/frictional: CalculiX surface-to-surface `*CONTACT PAIR` with linear penalty K = 50 E/h (+ `*FRICTION`), static steps start at 0.1 of the load; Code_Aster frictionless `DEFI_CONTACT` (continuous) + `STAT_NON_LINE` ramped over 10 increments, contact faces reoriented with `ORIE_PEAU`. Code_Aster friction: classic continuous `DEFI_CONTACT(FROTTEMENT='COULOMB')` with `NEWTON=_F(REAC_ITER=1)` and up to 200 iterations (as its 3D validation ssnv128). It works on first-order meshes with the slave face inside the master and no displacement condition on slave nodes; the adapter refuses quadratic meshes and slave/Dirichlet clashes up front. Fastener faces (bolt holes) that share nodes with a slave face are left out of its zone (`SANS_GROUP_NO`, `comm._contact_exclusions`): tied to the bolt and in contact too, the matrix is singular (LAGS_F1). Tried and failed here: quadratic tets (singular LAGS_C/LAGS_F; Code_Aster validates quadratic 3D friction on HEXA27 only), mortar `DEFI_CONT` + `MECA_NON_LINE` (validated in 2D and shells only; no convergence in 3D), discrete penalty. CalculiX inverted an element when the master overhung the slave; its test keeps coincident faces. No separation: CalculiX a surface-to-surface pair with `PRESSURE-OVERCLOSURE=TIED` and the stick slope TIED requires set to `SLIDE` (1e-6) of the penalty, μ 1e-6 (CalculiX refuses μ 0); Code_Aster `LIAISON_MAIL` with `DDL='DNOR'` (the catalogue's spelling, not DDL_ESCL), linear. Rough: CalculiX's linear pair with `*FRICTION` μ `ROUGH_MU` 1e3; Code_Aster's Coulomb zone at μ 10 (1e3 stopped Newton). Code_Aster's STAT_NON_LINE takes an absolute `RESI_GLOB_MAXI` (1e-6 E L u) when a contact study's only loads are imposed displacements (`comm._criterion`): an interface opening everywhere left the relative residual at 3 with 1e-13 N absolute. Static structural steps output reaction forces (`reaction_force`); `results.query.total` sums them over a selection.
- **History geometry** (`Geometry.history`, ADR 0014; operations listed in `geometry/history.py`'s docstring, profiles in `geometry/profile.py`) needs OCP (pixi env only; the `.venv` Python 3.14 has no OCP wheels): run `tests/test_naming.py` and `tests/integration/test_history_geometry.py` with `.pixi/envs/dev/bin/python -m pytest`. Lengths are SI; name box sides from geometry (OCCT's Left/Front/... faces don't follow the axes); use tight bounding boxes (`AddOptimal`); keep tool margins relative to the model size. OCCT's STEP/IGES writers assume millimetres (build test files in mm); `xstep.cascade.unit` is ignored in OCCT 8. Faces left split by a fuse are merged with `ShapeUpgrade_UnifySameDomain`, carrying names through its history. A cut removes a tool face lying on the part's surface (its name goes away).
- **Selection names (G3):** edge and point names are joined face names (`A|B`, `A|B|C`) and are unique per entity type only (a seam edge is named after its one face), so key anything by (entity, name). File-order names (`face-7`) are positional: trust them only when their anchor agrees. Selections with a `rule` have members recomputed on every regeneration. The GUI preview key covers the files' size and time, so a replaced file is noticed.
- **Sketches (py-slvs):** circle and arc constraints (`addCircle`, `addEqualRadius`, `addPointOnCircle`, `addDiameter`, `addArcLineTangent`) take no workplane argument; line and point ones do. `fix` (where-dragged) holds a point at its *stored* position, so the editor never drags a fixed point. SolveSpace distances are unsigned: which side a point stays on follows the starting positions, which is why solved positions are stored back. The SWIG binding's Python 3.12 deprecation warnings are filtered in pytest.
- **CalculiX reads at most 20 characters per field:** longer numbers are silently truncated (-8.67361737988404e-19 became -0.867 and inverted elements). Coordinates are written with 13 significant digits.
- **Revolved meshes (ADR 0077):** OCC can't revolve a face a whole turn and keep Gmsh's layers, so `mesh/revolved.py` revolves four quarter turns and fragments them together; its second order is serendipity (`Mesh.SecondOrderIncomplete`: hex20, wedge15), which CalculiX and Code_Aster take, with node reorders in `inp.ELEMENTS` and `post/vtk.py`. Peterson's Chart 3.4 (shouldered round bar in tension) is up to 40 % low for sharp fillets; check fillets against Tipton's Eq. 3.5 instead.
- **Threads (ADR 0076):** model the two smooth cylinders at one radius, the screw's minor (d3/2) measured best; a thread's springs act along the flank normals and carry results only through `thread_fields` (adapters only write). CalculiX crashed on contact-pair output written with no contact pair: threaded contacts are kept out of every contact-pair path (`c.thread is not None`). History-built named faces come back FORWARD whatever their solid says: `contacts._as_in_solid` reads the solid's orientation (a pin in a history bore was missed).
- **Contacts between joined bodies are parted after meshing** (ADR 0039 amended): a frictionless, frictional or tie contact whose two face groups share an entity (bodies of one part joined by Share faces, or parts fragmented together for other bonds) gets that entity's nodes duplicated by Gmsh's Crack plugin (`generate._part_contacts`; rim opened where only those two volumes meet, `_follow` moves the other faces of the body that took the new nodes); fragmenting bodies in separate groups loses a body's first join. `split_parts.plan` makes one part per body (a `keep` history step), references following; GUI One part per body…, MCP `parts_split`, CLI `split-parts`.
- **Touching bodies of one part are joined when meshed** (`Geometry.share_faces`, on by default; `generate._share_faces`): STEP stores each solid with its own faces, so without it two touching bodies share no nodes (42 nodes on the Hertz cylinder's split, 21 positions). Overlapping bodies are refused. A face the join splits (a block's top under a smaller block) is re-found by its pieces (`generate._pieces`: same kind, inside its placed bounding box, measures adding up). Off: each body meshed apart.
- **Part selections are matched within the part:** `generate_mesh` finds each part's faces only among its own bodies' boundaries, since identical parts can have coincident faces (two halves end to end).
- **Results store format 2** (`store.json`): an older store raises `stale_store`; delete the project's `results/` folder and rerun (results are a cache by run key). Arrays read back are read-only views of Arrow buffers. Never `sort_by` the fields table itself: it copies every array; sort the metadata and slice by offsets (`_Lists`).
- **The 3D view renders off screen** (`SceneView`), not in an on-screen OpenGL widget: on this Mac (Intel Iris, Retina) every on-screen embedding (pyvistaqt's native window, QOpenGLWidget) left unrefreshed rows along the bottom of the view; off-screen renders are always clean and take ~10 ms a frame. Change the scene through `Viewport` methods (they call `view.refresh()`); a bare `plotter.render()` does not update the widget.
- **View style and pyvista's camera:** `enable/disable_parallel_projection` move the camera each call (pyvista recomputes the position from a stale parallel scale), so `Viewport._apply_style` switches projection only on a change. View toolbar actions go through `Viewport` (`fit`, `look`, `set_style`, `image`), which also work, as no-ops recorded in `style`/`shown`, without OpenGL.
- **Labels over the 3D view are Qt widgets** (ADR 0032): `Viewport._draw_marks` places QLabels at projected points after each frame (`SceneView.drawn`). Hide a label before `deleteLater`: `processEvents()` (scripts, tests) never runs deferred deletes. VTK samples in single precision, so a probe at a node matches its value to about 1e-6, not exactly.
- **GUI tests** run on Qt's offscreen platform (`tests/test_gui.py` sets `QT_QPA_PLATFORM=offscreen`), which has no OpenGL: the viewport then shows a placeholder and records what it would draw in `Viewport.shown`, which tests check. Look at real renders by running the window on the native platform and saving `window.grab()`. Long work runs through `MainWindow.background` (thread pool); never block the GUI thread on a solve.
- **The built-in agent on macOS** gets no `render` tool in the GUI: off-screen VTK must render on the main thread there, and the agent runs on a worker. Remote providers get no images by default either (ADR 0015: outlines and summaries only unless `send_images = true`).
- **Unsupported structures are refused:** a stationary or transient solid-mechanics study whose component has no `fixed` or `displacement` feature reports the problem `unconstrained`, and `run_study` refuses it (CalculiX would return kilometres of rigid-body drift as a "result"). Free modal studies are allowed.
- **Agent edits in batches:** `Session.submit_batch` (MCP `submit` with a list) applies model edits all or none, as one history entry and one undo; runs and autonomy changes go on their own.
- **Faceted geometry** (STL/OBJ/3MF): Gmsh's `classifySurfaces` with reparametrization cuts faces into re-meshable patches (a box's top into two); `load_facets(reparametrize=True)` maps patches back to the unreparametrized faces users select, and the mesher's name map holds lists. Discrete entities have no OCC mass/centre; `model._discrete_props` computes them from the triangles.
- **OCP 8 collections** live in `OCP.collections` (`Sequence_TDF_Label`, `IndexedDataMap_TopoDS_Shape_List_...`); sewing tracks sub-shapes with `ModifiedSubShape`, not `Modified`.
- **Solver threads:** native and container runs get `OMP_NUM_THREADS` and CalculiX's `CCX_NPROC_EQUATION_SOLVER`/`_STIFFNESS`/`_RESULTS` (`jobs.runtime.thread_environment`; Settings > Solvers > Cores per run, automatic by default: 4, or one fewer than the physical cores on smaller machines (`machine.default_cores`, the maintainer, 2026-11-08), and Parallel processes per run, which share those cores (ADR 0053); the user's own values win). Code_Aster's export takes them (`code_aster.comm.resources`: `ncpus`, `mpi_nbcpu`, memory from `Runtime.memory`, Docker's VM in a container); run_aster ignores OMP_NUM_THREADS. Its MPI runs need an MPI build (`code_aster.mpi_build`: the `puzzle-code-aster:18.1-mpi` image, label `puzzle.mpi=openmpi`, or conda-forge's openmpi variant). Without them CalculiX factors on one core: a frictional contact took 62 min instead of 38. conda-forge's CalculiX has no PARDISO (`SOLVER=PARDISO` errors), so ADR 0051 builds one (`calculix-pardiso` env: compilers, MKL; `puzzle.solver_builds` compiles it, on Windows too with conda-forge's MinGW gcc/gfortran and mkl_rt; the installed app builds it once in the background, ADR 0068 step 4), found first by `jobs.runtime`: the bolted bracket 935 s → 246 s, the same answers; CalculiX picks PARDISO itself when built in. Newer compilers need CalculiX's old C let through (`-Wno-error=return-mismatch` and the like).
- **Windows (measured 2026-11-08):** `jobs.runtime.CONTAINER_FIRST` runs FEniCSx (no PETSc on win-64: SciPy SuperLU stalled 3D magnetics for 27+ min), Elmer (the Windows 26.2 build segfaulted on 19 of 31 tests) and Code_Aster (10-23 % faster) in their images when present; CalculiX stays native. Files a Linux container or host reads are written with `newline="\n"` (OpenFOAM's `Allrun` failed on `set -e\r`; also Elmer's files, run scripts, the runner's script). Docker there runs containers as root, so images launching OpenMPI set `OMPI_ALLOW_RUN_AS_ROOT`. `SERIAL_BLAS` (`BLIS_NUM_THREADS=1`) goes with every run: the Linux FEniCSx env links BLIS, which read OMP_NUM_THREADS under MUMPS's threads and never finished LE1 (8 s with it).
- **Face areas** (`common.surface_area`) integrate curved second-order faces as the solvers do: a force spread as F / A on flat-triangle areas came out 0.2 % low on a face with a hole (Code_Aster).
- **Solver logs** are capped at 256 MB (`jobs.runner.MAX_LOG_BYTES`) and read from the end on failure (`log_tail`).
- **Gmsh from threads:** OpenCASCADE keeps per-thread state from its first user; if that thread exits and another thread uses Gmsh, the process segfaults. `gmsh_session` first initialises Gmsh on a resident daemon thread. MCP runs sync tools on worker threads, so this matters.
- **MCP SDK 2.x:** `from mcp.server.mcpserver import MCPServer` (FastMCP was renamed); results are `structured_content`/`is_error`. Annotate tool returns as `dict[str, Any]`, not bare `dict`, or the output is unstructured text.
- **history.jsonl** is append-only and part of the project record: entries `command`, `undo`, `proposal`, `decision`, `confirmation_request`. Undo restores the logged before-snapshots and refuses if the objects changed since. A version restore (ADR 0059) is a `command` entry (`restore_version`, with `files_from`), so undo takes it back.
- **Versions in tests:** every session that changes a project writes `versions/` there (ADR 0059); a test that compares a project folder's files must leave `versions/` out, or set `versions.auto` off.
- **Test isolation from the user:** `tests/conftest.py` points `PUZZLE_USER_DIR` at a scratch folder (settings.toml, agent.toml), resets preferences before each test (`_fresh_settings`), and GUI tests that type millimetres use the `engineering_units` fixture.
- **Coordinate systems (ADR 0049):** `CoordinateSystem` is Cartesian, cylindrical or spherical; read `orientation()` (from `angles`, `points` or directions), `centre()` and `frames(points)`, never `origin`/`axis` directly. Results in a system are a post step (`post/axes.py` `in_axes`): vectors and tensors rotated per node, the component slots unchanged and named by `quantities.catalog(fields, axes)`; `displacement_global` keeps the warp. The results bar's In axes starts at Global for each result shown.
- **Derived coordinate systems (ADR 0049 step 3):** a system from a face or edge, attached to a part, or relative to another is resolved by `puzzle.axes.absolute(project, cs, root)` (`run_study` hands adapters `resolved_project`); never read such a system's `centre()`/`orientation()` unresolved. Material directions: `MaterialAssignment.axes` (CalculiX `*ORIENTATION`; Code_Aster `MASSIF` ANGL_REP or ANGL_AXE, its cylindrical L T N being axial, tangential, radial, so `comm.CYLINDRICAL` reorders the constants; Elmer and FEniCSx refuse orthotropic and anisotropic models).
- **Local axes (ADR 0037):** `common.globalize` turns Cartesian forces and full Cartesian displacements into global ones before writing; what's left (cylindrical, or some components only) each adapter writes itself, and `Capabilities.axes_features` (`"displacement:cylindrical"`, `":partial"`) says which. Code_Aster: when every constraint is a function, the plain `load` charge is left out (an empty `AFFE_CHAR_MECA` is a syntax error).
- **The preload step (ADR 0037 amended):** `puzzle.preload.applied` (in `run_study`, after `bolts.resolved`) puts a preload-only step in front of a first static step that tightens bolts and loads (`Study.preload_step` auto/always/never; auto on CalculiX and Code_Aster). Loads move to later steps, and a nonzero prescribed displacement is held at zero while preloading. The step's results are kind `preload`. Run keys come from the project before it (`keyed`), plus the step's index (`graph.run_hashes`). Code_Aster chains static steps that tighten bolts into one `STAT_NON_LINE` result (`comm.chained`, `Adapter.chains`): one call per step, `ETAT_INIT` from the last, windowed charges with multiplier functions, the pretension's drive in its step, then `DIDI` locked; the reader numbers steps by time (`job.chain.json`).
- **Bolt pretension (ADR 0037, CalculiX):** the deck cuts the mesh at the section (twin nodes, the elements on one side moved onto them, `*EQUATION` u_twin − u = n u_ref), because `*PRE-TENSION SECTION` moves only elements with a face on the section and leaves tets joined at edges. Helper node ids, in order past the mesh's: rigid-body nodes, pretension reference nodes, twins, spring grounds. Spring grounds are held in each step (an `OP=NEW` would drop a model-level hold). `Feature.steps` limits a feature to some solve steps: CalculiX writes it per step (a later step resets each load card it doesn't write, since `OP=NEW` is per card); split studies get a project copy per step (`solve._in_step`). Code_Aster writes elastic supports and pretension through point elements added to the MED mesh (`comm._Points`: one group per node; `DIS_T`, `K_T_D_N` with `REPERE='LOCAL'`), the same cut as CalculiX (`common.section_cuts`), `LIAISON_DDL` to a reference node with a 1e-9 stiffness on its DX; helper nodes are dropped from results by `common.mark_mesh_nodes`/`drop_helper_nodes`, and value-less table rows ("-") are skipped. Compression-only supports: CalculiX `GAPUNI` to grounds in an `NLGEOM` step (gaps aren't switched in a linear one); Code_Aster `DIS_CHOC` on the point elements, local x into the face.
- **Bolt sizes:** `bolts.SIZES` holds M3–M64, UNC to 4 in and UNF to 1 1/2 in, sorted by diameter per standard (the size listed first stays first, so a bolt type's nearest size is stable); M39 and up take dw = 0.95 s min (ISO 4014 grade B).
- **Bolts (ADR 0050):** a bolt (`BeamFastener`) may name a `BoltType` (`puzzle.bolts`: standard sizes, stress areas, preload as a force, % of yield or a torque, joint style); `bolts.resolved(project)` fills what a bolt leaves unset before checking and solving, and `bolts.with_joints` (in `run_study`, after meshing) adds the head/nut annuli and tapped threads as mesh face groups and points the bolt's ends at them. The generator is `puzzle.bolt_generator` (rules kept in `Component.bolt_rules`, sets, picks; stacks as one bolt with `through`; `ground_unpaired`, `same_part`, `bearing_faces`), the docked table `gui/bolt_table.py` + `gui/bolt_results.py`. A bolt to ground (`ground`, no `target`) ends at a held point: read a bolt's ends with `common.fastener_ends`, never `fastener_end(f.target)`. Bearing rings are the history operation `imprint` (`<step>/annulus`); a bolt's `bearing` names them. The generator builds bolts untyped first, so typed ones must drop the defaults it filled in (joint, formulation, ends). Bolt rules, groups and `through` are left out of content hashes (`project/graph._own`).
- **CalculiX beams (ADR 0055):** B31/B32 expand into solids of RECT, CIRC, PIPE or BOX outlines; PIPE and BOX only on B32R (the adapter writes B32R for such parts and asks for second-order meshes). Its U1 general beam gives torsion G (I11 + I22) / L (`e_c3d_u1.f`), not G J, so open table sections (I, channels, tees, angles) are written as exact Timoshenko springs instead (`calculix/spring_beams.py`: per element, both orders, a second-order one as two segments; a rotation node per mesh node, linear rigid arms by `*EQUATION` to the segment's middle, six SPRING2 in the section's frame, `common.timoshenko_springs`; a zero spring N to its rotation node, since the .frd holds element nodes only; lumped MASS, no rotary inertia; `beam_forces` and the nodes' reactions read from the springs' end reactions, not from displacements, which the .frd prints to six digits), refusing heat, thermal loads, buckling, NLGEOM, prestress, plasticity, Rayleigh damping, centrifugal loads and shared nodes; Code_Aster takes every shape (`SECTION='GENERALE'`, IY strong, AY = A/A1).
- **Beam fasteners (ADR 0027):** `Component.connectors` (`BeamFastener`) are beam bolts by default (`formulation`): CalculiX writes the exact Timoshenko equivalent, the ends' spiders carrying a middle node each and six `SPRING2` springs between them in the bolt's frame (`common.beam_bolt_stiffness`; its U1 beam is wrong for short beams and its B31 beams can't join rigid bodies); Code_Aster a `POU_D_T` beam (no point element on its end nodes: EFGE_NOEU averages over a node's elements). In a pretension cut the spider's node must be the dependent term: CalculiX passes no force through a spring whose node is the dependent term of an equation with an opening. `formulation="solid"` keeps the meshed bolt (`common.bolt_mesh`). Rigid ends: one rigid body with the hole (`*RIGID BODY`, `LIAISON_SOLIDE`); distributing: the bolt end rigid with two helper nodes, RBE3 to the hole (CalculiX `*EQUATION` solved for six face dofs, `_rbe3_equations`, so nothing cascades; Code_Aster `LIAISON_RBE3` to a `DIS_TR` master). Forces are the bolt end faces' reactions summed (`common.fastener_values`), as the global field `fastener`. CalculiX set names keep signs (`+z` → P, `-z` → M): box sides used to share a set.
- **Material models** (`Material.models`: plasticity, orthotropic elasticity, hyperelasticity, anisotropic conductivity; `Material.solver_keywords`): an adapter writes those in `Capabilities.material_models` (`material_keywords` for keywords) and `Adapter.check` refuses the rest, only for studies that solve the model's physics. Plasticity is written by CalculiX (`*PLASTIC`, stepped static steps, PEEQ out) and Code_Aster (`VMIS_ISOT_TRAC` in `STAT_NON_LINE`), benchmarked in `tests/integration/test_plasticity.py`; orthotropic elasticity and anisotropic conductivity by CalculiX and Code_Aster (ADR 0049, `test_orthotropic.py`); hyperelasticity is refused everywhere so far. A study whose materials lack a needed property reports `incomplete_material` (`Project.problems`), so runs are refused before writing input.
- **Material data:** only `generic.toml` ships. The maintainer's full library is generated from `Materials_Hunt_List.xlsx` by `scripts/import_materials.py` into the user library (`puzzle.materials.user_library_path()`, outside the repo) and must never be committed. Tests set `PUZZLE_MATERIALS=""` (generics only) in `tests/conftest.py`; anything tests or examples use must be generic.
