# Puzzle

Open-source (GPL-3.0-or-later) FEM/CFD pre- and post-processor: one solver-neutral model run on CalculiX, Elmer, Code_Aster, FEniCSx, Code_Saturne and OpenFOAM, aiming for Ansys/COMSOL usability. Decisions live in `docs/adr/` (read the index before changing architecture); the shareable design doc is a Claude Doc: https://claude.ai/code/artifact/7e7a31c7-a7a6-49b3-97ed-05307493943f. Keep both in sync when a decision changes.

## Workflow

- Work on the `development` branch. Push to `main` only when the maintainer says so.
- Contributors are the maintainer and Claude; no CLA/DCO.
- Commit and push only when asked.
- New architectural decision → new ADR from `docs/adr/template.md`, plus a row in `docs/adr/README.md`.

## Commands

Environments come from pixi (`pixi.toml`, ADR 0013). Each native solver has its own environment.

```sh
pixi run -e dev check          # ruff lint + format check + all tests incl. native CalculiX runs
pixi run -e dev pytest -k name # one test
pixi install -e fenicsx        # other native solvers: fenicsx, code-aster (linux-64/win-64)
pixi run -e dev import-materials "<path>/Materials_Hunt_List.xlsx"
pixi run -e dev puzzle gui examples/cantilever   # the desktop GUI
pixi run -e dev puzzle agent-key set            # store the Claude key in the keychain (hidden prompt)
pixi run -e dev puzzle ask PROJECT "question"    # the built-in agent in a terminal
```

A plain `.venv` also works (`pip install -e ".[dev]"`); set `PUZZLE_SOLVER_PATH=$PWD/.pixi/envs/calculix/bin` so solver tests find `ccx`. Started from a pixi env without `pixi run` (the env's own `puzzle`, an editor's Python, an MCP client), Puzzle still finds the solver envs beside its own (`jobs.runtime.pixi_solver_dirs`), after PUZZLE_SOLVER_PATH and PATH. Docker and Podman are found off PATH too, where their installers put them (`ENGINE_DIRS`, e.g. Docker Desktop's app folder on macOS), and that folder goes on the engine's PATH.

Dynamics (ADR 0041): a `transient` step solving solid mechanics is structural dynamics (Newmark, `time_step`/`end_time`, `method` direct or modal, `hht_alpha`), a `frequency_domain` one harmonic response (`frequencies` as text, or start/end/points/spacing); Rayleigh `rayleigh_alpha`/`rayleigh_beta` per study (`common.rayleigh`; Code_Aster's AMOR_ALPHA is the stiffness one), `damping_ratio` with the modal method only; CalculiX `*DYNAMIC, DIRECT, ALPHA=0` or a stored `*FREQUENCY` step then `*MODAL DYNAMIC`/`*STEADY STATE DYNAMICS` (one step per listed frequency), Code_Aster `DYNA_NON_LINE` and `DYNA_VIBRA` HARM PHYS (complex parts written as two real results); harmonic results are `displacement_amplitude`, `displacement_phase` and `displacement` at the peak instant (`common.harmonic_fields`); force and pressure may follow an amplitude; every CalculiX `*STEP` is tagged `** puzzle step k` (0 = helper) and results are mapped back by `inp.step_owners`; benchmarks in `tests/integration/test_dynamics.py`. Buckling (ADR 0028): a `buckling` step (settings `modes`, `preload` = hold the static step just before it, `shift` on Code_Aster only) on CalculiX (`*BUCKLE`; with a preload the static step gets NLGEOM and the buckle step PERTURBATION; the reader drops each buckle step's static block and numbers modes) and Code_Aster (`RIGI_GEOM` + `CALC_MODES` `MODE_FLAMB`, `CHAR_CRIT` = load factor; `run_study` hands a preloaded buckling step its static step); results are one step per mode, value = load factor, labelled by `StepResult.label()`; benchmarks in `tests/integration/test_buckling.py`. Body loads (ADR 0037): `gravity`, `acceleration` (inertia −a) and `rotation` (centrifugal) on a body selection, on CalculiX, Code_Aster, Elmer and FEniCSx (`adapters.common.body_load`), benchmarked in `tests/integration/test_body_loads.py`; they make density required. Remote loads: `remote_force` (an RBE3-equivalent traction, `adapters.common.remote_load`, integrated on the curved faces) and `remote_displacement` (a rigid motion field) on all four FE solvers, `remote_force_rigid` on CalculiX (`*RIGID BODY`, extra nodes past the mesh's ids) and Code_Aster (`LIAISON_SOLIDE`); torsion benchmarks in `tests/integration/test_remote_loads.py`. Beams (ADR 0027): a `polyline` geometry step meshes into line elements (`Mesh.beam_blocks()`: line blocks of line-body parts; a solid's mesh also has line blocks on named edges, which are not elements); `Component.beam_sections` gives each line part a section; CalculiX B31/B32 (`OUTPUT=2D` maps expanded results back) and Code_Aster POU_D_T (order 1 only; `beam_forces` field), refused on Elmer and FEniCSx (`Capabilities.beams`); `tests/integration/test_beams.py`. Shells (ADR 0027): `sheet`/`curved_sheet` geometry steps mesh into triangles (`Mesh.shell_blocks()`); `Component.shell_sections` gives a thickness and offset; CalculiX S6/S8 (S3 refused: it locks; shell pressure written as −p, since its P pushes along the element normal) and Code_Aster DKT (order 1 only; `FORCE_COQUE`); a positive pressure on a sheet pushes against the face's normal; `tests/integration/test_shells.py`. An `Amplitude` (factor against time) on a feature (`Feature.amplitude`) varies it in transient steps; only heat flux so far (`Capabilities.amplitude_features`), refused elsewhere. Transient steps take `time_step` and `end_time` settings, and `time_scheme` (default `backward_euler` on every solver, so shoot-outs compare like with like; also `crank_nicolson`, `bdf2`, `theta` with a `theta` setting, where the capability matrix's `time_schemes` allows); heat physics takes `initial_temperature`. Heat transfer uses a material's temperature tables (conductivity, specific heat, density) by default, which makes it nonlinear; the physics setting `temperature_dependent_materials = false` uses the single values instead (closed-form benchmarks do this). `tests/integration/test_nonlinear_conduction.py` checks the tables against the Kirchhoff solution (all four FE solvers within 0.002 K) and in a transient shoot-out. Results come back as one step per output time (`StepResult.value` = time). Whole-model values (e.g. stored electric energy) are fields with `location="global"`.

Solver tests in `tests/integration/` skip when the solver isn't available; `tests/solvers.py` `over("elmer", "fenicsx")` parametrizes a test over solvers. Rendering tests run only with `PUZZLE_RENDER_TESTS=1`; check renders by looking at the PNG (`puzzle show ... --screenshot`). Container runs: `PUZZLE_RUNTIME=docker pytest tests/integration` after building images in `containers/`.

## Conventions

- Everything is SI internally (m, kg, s, N, Pa, K). Imported geometry is converted to metres; `Quantity.to_si()` converts user values. Never pass units implicitly to a solver.
- Adapters only claim a capability once a benchmark for it passes. Elmer's mechanical contact is bonding only (mortar tie); its slide/friction/stick are `experimental`.
- Tests compare against closed-form or published answers with stated tolerances, not snapshots.
- Match the surrounding code: dataclasses/Pydantic, type hints, short docstrings that say why.
- **Adapters take transferred fields as `inputs`** (`write_input(..., inputs)`); one that can't apply an input must refuse it (`base.refuse_inputs`), never ignore it. Temperature loads (role `load`) work on CalculiX (`*TEMPERATURE` per step, initial temperature = reference), FEniCSx (thermal strain in the weak form), Code_Aster (field built in the .comm from `transferred-temperature.txt`, matched by coordinates, `AFFE_VARC`) and Elmer (an ASCII restart file `puzzle-temperature.result` in Elmer node order). Prestress (role `prestress`, CalculiX): the static source study on the same component is replayed as an NLGEOM first step and the study's own steps become `PERTURBATION` steps; a `.prestress` marker tells the reader to drop the replayed step's results (`test_prestress.py` matches a 1D beam with geometric stiffness to 0.1%). the reference is the structural physics' `reference_temperature` (default 20 °C). `tests/integration/test_transfers.py` checks thermal bending across solver pairs and an interpolated mesh.
- **Multi-step studies:** CalculiX writes every solve step in one deck; adapters with `max_solve_steps = 1` (Elmer, Code_Aster, FEniCSx, Code_Saturne) get the study split by `run_study`, one job per step on the same mesh. Those steps are independent analyses; sequencing state from one step to the next is what transfers are for.
- **The GUI shows names, never ids or internal keys.** Anything with a fixed set of values is a dropdown of readable names that stores the real value: `gui/choices.py` (`choices(project, obj, path)`, `label`, `solver_label`) drives the properties panel; menus, `window.choose` (takes (name, value) pairs), the tree, history lines, Problems, the agent panel and the results bar use the same labels. Quantities' units are checked when typed (`units.known`). New GUI elements follow this. Creating something asks everything in one dialog (`window.ask_form`, `gui/quick_form.py`; tests fill it with `tests/forms.py` `fill`), never a chain of popups. Long forms use `gui/form.py` `FormPanel` (ADR 0036): sections, label | field | unit rows, descriptions from `DESCRIPTIONS`, the blocking message on top. Never name a widget attribute after a QWidget method (`height`, `width`, `size`, `font`). `tests/test_gui_names.py` checks every tree item's properties for ids, `null`, "N items" and snake_case keys (ADR 0029); panels that belong to one context (the results bar, the ribbon) show through `MainWindow.set_context`, and mode-specific fields hide through `APPLIES` in `gui/properties.py`.
- **Display units (ADR 0024):** values are stored as typed (and converted to SI for solvers); what the GUI shows follows Settings → Units (default SI: a 2.5 mm size shows as 0.0025 m; a bare number typed is in the unit shown). Use `units.shown`/`pretty` and `settings.length_unit()` in new GUI code, never a hard-coded mm. Preferences never change results. A project may switch on its own system (ADR 0030, the `ProjectUnits` object, kind `units`); `settings.use_project` applies it on refresh, so `current().display_units()` is always what's shown; tests reset it in `conftest._fresh_settings`.
- **Solver settings (ADR 0023):** shared ones (`adapters.settings.SHARED`) live on each solve step; each solver's own in `Study.solver_settings[solver]` from its `settings_schema()`, pass-through in `Study.expert_settings[solver]` (checked by `check_expert`, placed or refused, never dropped); run keys cover only the running solver's blocks; write only what is set so defaults never move results. CalculiX applies them per written step (`inp.with_settings`), Code_Aster as keyword overrides on the .comm (`code_aster/expert.py`), Elmer as SIF section overrides (`elmer/sif_edit.py`), FEniCSx through `case.json` settings and PETSc options, Code_Saturne through its case model and setup.xml paths, OpenFOAM through `foamDictionary` in `Allrun`; `Capabilities.shared_settings` says which shared ones each takes (others refused). Presets are `SettingsPreset` (kind `preset`).
- **Every project change goes through `puzzle.commands.Session`** (CLI, GUI, scripts, agents); no client writes project files itself. New user actions become commands in `commands/model.py`. Errors a client can act on are `PuzzleError` with a code from `puzzle.errors.CODES`.

## Gotchas

- **Gmsh is global state.** Always use `puzzle.geometry.gmsh_session()`; it holds a lock and sets OCC import units to metres. Don't nest sessions.
- **OpenCASCADE is serialised:** `geometry.session.occ_lock` (re-entrant) wraps `regenerate`, `read_cad`, `write_brep`, `resolve_geometry`, `check_geometry`, and every Gmsh session takes it before its own lock. Gmsh and OCP share one OCCT; concurrent GUI jobs (a preview and a selection check) failed inside it (`NCollection_IndexedMap::FindKey`, bodies lost while placing). New OCC work off the GUI thread must take it too.
- **OCC pads bounding boxes** by ~1e-7 m. Plane tests need a tolerance of at least 1 µm.
- **Entity names** (`face-3`) follow STEP file order; signatures (kind, measure, centre) re-find them after placement or fragmenting.
- **Element node order:** Gmsh differs from CalculiX, Elmer and VTK for tet10 (last two edge nodes swap). Adapters own the reordering; shared face lookups live in `adapters/common.py`.
- **Custom PDE weak forms** are evaluated with `eval` and no builtins in `study.py` (`UFL_NAMES` plus the unknown, `v_<u>`, `<u>_n`, `dt`, coefficients, `x`, `dx`/`ds` taking selection names, `prop(...)`). That limits mistakes, not a determined attacker: treat projects with equations as code. dolfinx wants each cell tagged once, so the case mesh tags volumes by material selections (or parts) only.
- **FEniCSx `study.py`** runs inside the FEniCSx env and must not import puzzle. dolfinx 0.11 `LinearProblem` needs `petsc_options_prefix`; MUMPS is used only if PETSc has it. Windows dolfinx has no PETSc, so `study.py` falls back to SciPy (SuperLU, ARPACK; CG for the stress projection); `PUZZLE_FENICSX_BACKEND=scipy` forces that path for testing (LE1 ~54 s vs ~10 s with PETSc).
- **Code_Saturne specifics:** an imposed wall flux is positive leaving the fluid (the adapter flips Puzzle's sign); turbulent intensity is in percent; the steady algorithm takes thousands of iterations for conduction-dominated scalars (use `pseudo_time_step`). RANS wall functions under-predict friction ~15% at Re_tau ~ 400; benchmark them at Re ≥ 1e5.
- **OpenFOAM's `etc/bashrc`** reads the positional arguments it is sourced with (it can source files named there), so the image's entrypoint clears them first. Its pressure is kinematic (p/ρ); the adapter writes and reads Pa. `scalarTransport` is not under-relaxed and sits in `residualControl`, or simpleFoam stops when only the flow has converged.
- **Code_Saturne's Gmsh reader** names groups by physical tag number, not name: zones select `"2"`, not `"Inlet"` (`write_med` returns the tags). Results are per cell (`location="element"`), matched to Puzzle elements by node-average centres (`match_points`, float32-tolerant).
- **Temperature tables per solver:** CalculiX `*CONDUCTIVITY` value/temperature lines plus tight `*CONTROLS, PARAMETERS=FIELD` (its defaults stop 0.2 K short); Elmer `Variable Temperature` tables with nonlinear iterations; Code_Aster `THER_NL` (LAMBDA and enthalpy BETA functions) with `THER_NON_LINE`, steady via `ETAT_INIT=_F(STAT='OUI')`; FEniCSx a closed-form piecewise-linear UFL expression and Picard iteration. Code_Aster is written with `PARM_THETA` (1.0 by default, not its own 0.57). With temperature tables Code_Aster steps the enthalpy, the others rho cp(T); they differ by O(dt) (0.7 K at dt = 5 s in the shoot-out, 0.15 K at 1 s), Code_Aster being closer to the converged answer.
- **Time schemes at t = 0:** backward Euler agrees across all four solvers to 3 decimals and BDF2 between Elmer and FEniCSx. For theta < 1 the starting state matters: Code_Aster and FEniCSx start from the given initial field, while Elmer appears to apply the boundary values to the starting state first, and its Crank-Nicolson damps the initial jump (plain CN from a stepped start oscillates: 18.7 K in a FEniCSx experiment). So theta-scheme results differ between Elmer and the other two after a sudden load; prefer backward Euler or BDF2 there.
- **Code_Aster 18** needs `INCREMENT` even for steady `THER_LINEAIRE`; table numbers need `FORMAT_R` (default keeps 5 digits). Containers run as your uid with `HOME=/tmp` (run_aster needs a home).
- **Elmer output** lands in the mesh directory (`mesh/case_t0001.vtu`). Points come in Elmer node order (no point ids); `GeometryIds` there is cell data. Eigenvalues (omega^2) are parsed from the solver log.
- **CalculiX `.frd`** is fixed width (values can touch); match record tags on the first token. Modal block values are frequencies in Hz.
- **Native solver runs** must look activated: `NativeRuntime.environment()` puts the conda/pixi env on PATH and sets `CONDA_PREFIX` (Windows otherwise fails with 0xC0000135). Elmer from conda also needs `ELMER_HOME` = env prefix.
- **Elmer image** is built without MUMPS (Debian trixie lacks ParMETIS).
- **Elmer magnetics:** the A-V edge system stalls under GCR/BiCGStab here, so it is solved directly (Elmer then tree-gauges it). Unlisted SIF keywords such as `Use Magnetic Norm` need an explicit type (`Logical True`), or parsing fails. Lowest-order edge elements give B constant per element; nodal B is an average, so check it away from material interfaces and use the stored energy for the whole field.
- **Local mesh sizes** are Gmsh `Constant` fields over the selection's entities (min-combined background field); point sizes alone barely refine curved bodies.
- **Contacts:** adapters must refuse contacts they don't write (`common.check_contacts`, code `unsupported`); conformal bonds need nothing (shared nodes). Nonconformal bonds: CalculiX `*TIE` (source = slave surface, target = master; works for heat too), Code_Aster `LIAISON_MAIL` (source face into the target part's volume; structural only). `tests/integration/test_contact.py` uses `conftest_geometry.split_bar_project`. Don't put SPCs on CalculiX tie slave nodes: the conflict floods the log with cascade warnings. Frictionless/frictional: CalculiX surface-to-surface `*CONTACT PAIR` with linear penalty K = 50 E/h (+ `*FRICTION`), static steps start at 0.1 of the load; Code_Aster frictionless `DEFI_CONTACT` (continuous) + `STAT_NON_LINE` ramped over 10 increments, contact faces reoriented with `ORIE_PEAU`. Code_Aster friction: classic continuous `DEFI_CONTACT(FROTTEMENT='COULOMB')` with `NEWTON=_F(REAC_ITER=1)` and up to 200 iterations (as its 3D validation ssnv128). It works on first-order meshes with the slave face inside the master and no displacement condition on slave nodes; the adapter refuses quadratic meshes and slave/Dirichlet clashes up front. Tried and failed here: quadratic tets (singular LAGS_C/LAGS_F; Code_Aster validates quadratic 3D friction on HEXA27 only), mortar `DEFI_CONT` + `MECA_NON_LINE` (validated in 2D and shells only; no convergence in 3D), discrete penalty. CalculiX inverted an element when the master overhung the slave; its test keeps coincident faces. Static structural steps output reaction forces (`reaction_force`); `results.query.total` sums them over a selection.
- **History geometry** (`Geometry.history`, ADR 0014; operations listed in `geometry/history.py`'s docstring, profiles in `geometry/profile.py`) needs OCP (pixi env only; the `.venv` Python 3.14 has no OCP wheels): run `tests/test_naming.py` and `tests/integration/test_history_geometry.py` with `.pixi/envs/dev/bin/python -m pytest`. Lengths are SI; name box sides from geometry (OCCT's Left/Front/... faces don't follow the axes); use tight bounding boxes (`AddOptimal`); keep tool margins relative to the model size. OCCT's STEP/IGES writers assume millimetres (build test files in mm); `xstep.cascade.unit` is ignored in OCCT 8. Faces left split by a fuse are merged with `ShapeUpgrade_UnifySameDomain`, carrying names through its history. A cut removes a tool face lying on the part's surface (its name goes away).
- **Selection names (G3):** edge and point names are joined face names (`A|B`, `A|B|C`) and are unique per entity type only (a seam edge is named after its one face), so key anything by (entity, name). File-order names (`face-7`) are positional: trust them only when their anchor agrees. Selections with a `rule` have members recomputed on every regeneration. The GUI preview key covers the files' size and time, so a replaced file is noticed.
- **Sketches (py-slvs):** circle and arc constraints (`addCircle`, `addEqualRadius`, `addPointOnCircle`, `addDiameter`, `addArcLineTangent`) take no workplane argument; line and point ones do. `fix` (where-dragged) holds a point at its *stored* position, so the editor never drags a fixed point. SolveSpace distances are unsigned: which side a point stays on follows the starting positions, which is why solved positions are stored back. The SWIG binding's Python 3.12 deprecation warnings are filtered in pytest.
- **CalculiX reads at most 20 characters per field:** longer numbers are silently truncated (-8.67361737988404e-19 became -0.867 and inverted elements). Coordinates are written with 13 significant digits.
- **Part selections are matched within the part:** `generate_mesh` finds each part's faces only among its own bodies' boundaries, since identical parts can have coincident faces (two halves end to end).
- **Results store format 2** (`store.json`): an older store raises `stale_store`; delete the project's `results/` folder and rerun (results are a cache by run key). Arrays read back are read-only views of Arrow buffers. Never `sort_by` the fields table itself: it copies every array; sort the metadata and slice by offsets (`_Lists`).
- **The 3D view renders off screen** (`SceneView`), not in an on-screen OpenGL widget: on this Mac (Intel Iris, Retina) every on-screen embedding (pyvistaqt's native window, QOpenGLWidget) left unrefreshed rows along the bottom of the view; off-screen renders are always clean and take ~10 ms a frame. Change the scene through `Viewport` methods (they call `view.refresh()`); a bare `plotter.render()` does not update the widget.
- **View style and pyvista's camera:** `enable/disable_parallel_projection` move the camera each call (pyvista recomputes the position from a stale parallel scale), so `Viewport._apply_style` switches projection only on a change. View toolbar actions go through `Viewport` (`fit`, `look`, `set_style`, `image`), which also work, as no-ops recorded in `style`/`shown`, without OpenGL.
- **Labels over the 3D view are Qt widgets** (ADR 0032): `Viewport._draw_marks` places QLabels at projected points after each frame (`SceneView.drawn`). Hide a label before `deleteLater`: `processEvents()` (scripts, tests) never runs deferred deletes. VTK samples in single precision, so a probe at a node matches its value to about 1e-6, not exactly.
- **GUI tests** run on Qt's offscreen platform (`tests/test_gui.py` sets `QT_QPA_PLATFORM=offscreen`), which has no OpenGL: the viewport then shows a placeholder and records what it would draw in `Viewport.shown`, which tests check. Look at real renders by running the window on the native platform and saving `window.grab()`. Long work runs through `MainWindow.background` (thread pool); never block the GUI thread on a solve.
- **The built-in agent on macOS** gets no `render` tool in the GUI: off-screen VTK must render on the main thread there, and the agent runs on a worker. Remote providers get no images by default either (ADR 0015: outlines and summaries only unless `send_images = true`).
- **Unsupported structures are refused:** a stationary or transient solid-mechanics study whose component has no `fixed` or `displacement` feature reports the problem `unconstrained`, and `run_study` refuses it (CalculiX would return kilometres of rigid-body drift as a "result"). Free modal studies are allowed.
- **Agent edits in batches:** `Session.submit_batch` (MCP `submit` with a list) applies model edits all or none, as one history entry and one undo; runs and autonomy changes go on their own.
- **Faceted geometry** (STL/OBJ/3MF): Gmsh's `classifySurfaces` with reparametrization cuts faces into re-meshable patches (a box's top into two); `load_facets(reparametrize=True)` maps patches back to the unreparametrized faces users select, and the mesher's name map holds lists. Discrete entities have no OCC mass/centre; `model._discrete_props` computes them from the triangles.
- **OCP 8 collections** live in `OCP.collections` (`Sequence_TDF_Label`, `IndexedDataMap_TopoDS_Shape_List_...`); sewing tracks sub-shapes with `ModifiedSubShape`, not `Modified`.
- **Solver logs** are capped at 256 MB (`jobs.runner.MAX_LOG_BYTES`) and read from the end on failure (`log_tail`).
- **Gmsh from threads:** OpenCASCADE keeps per-thread state from its first user; if that thread exits and another thread uses Gmsh, the process segfaults. `gmsh_session` first initialises Gmsh on a resident daemon thread. MCP runs sync tools on worker threads, so this matters.
- **MCP SDK 2.x:** `from mcp.server.mcpserver import MCPServer` (FastMCP was renamed); results are `structured_content`/`is_error`. Annotate tool returns as `dict[str, Any]`, not bare `dict`, or the output is unstructured text.
- **history.jsonl** is append-only and part of the project record: entries `command`, `undo`, `proposal`, `decision`, `confirmation_request`. Undo restores the logged before-snapshots and refuses if the objects changed since.
- **Test isolation from the user:** `tests/conftest.py` points `PUZZLE_USER_DIR` at a scratch folder (settings.toml, agent.toml), resets preferences before each test (`_fresh_settings`), and GUI tests that type millimetres use the `engineering_units` fixture.
- **Local axes (ADR 0037):** `common.globalize` turns Cartesian forces and full Cartesian displacements into global ones before writing; what's left (cylindrical, or some components only) each adapter writes itself, and `Capabilities.axes_features` (`"displacement:cylindrical"`, `":partial"`) says which. Code_Aster: when every constraint is a function, the plain `load` charge is left out (an empty `AFFE_CHAR_MECA` is a syntax error).
- **Bolt pretension (ADR 0037, CalculiX):** the deck cuts the mesh at the section (twin nodes, the elements on one side moved onto them, `*EQUATION` u_twin − u = n u_ref), because `*PRE-TENSION SECTION` moves only elements with a face on the section and leaves tets joined at edges. Helper node ids, in order past the mesh's: rigid-body nodes, pretension reference nodes, twins, spring grounds. Spring grounds are held in each step (an `OP=NEW` would drop a model-level hold). `Feature.steps` limits a feature to some solve steps: CalculiX writes it per step (a later step resets each load card it doesn't write, since `OP=NEW` is per card); split studies get a project copy per step (`solve._in_step`). Code_Aster writes elastic supports and pretension through point elements added to the MED mesh (`comm._Points`: one group per node; `DIS_T`, `K_T_D_N` with `REPERE='LOCAL'`), the same cut as CalculiX (`common.section_cuts`), `LIAISON_DDL` to a reference node with a 1e-9 stiffness on its DX; helper nodes are dropped from results by `common.mark_mesh_nodes`/`drop_helper_nodes`, and value-less table rows ("-") are skipped. Compression-only supports: CalculiX `GAPUNI` to grounds in an `NLGEOM` step (gaps aren't switched in a linear one); Code_Aster `DIS_CHOC` on the point elements, local x into the face.
- **Beam fasteners (ADR 0027):** `Component.connectors` (`BeamFastener`) are written as small solid bolts (`common.bolt_mesh`, quadratic tets between the ends' centres), not beam elements: CalculiX ties no beam node into a rigid MPC and its beam-rotation equations left joints near a hinge. Rigid ends: one rigid body with the hole (`*RIGID BODY`, `LIAISON_SOLIDE`); distributing: the bolt end rigid with two helper nodes, RBE3 to the hole (CalculiX `*EQUATION` solved for six face dofs, `_rbe3_equations`, so nothing cascades; Code_Aster `LIAISON_RBE3` to a `DIS_TR` master). Forces are the bolt end faces' reactions summed (`common.fastener_values`), as the global field `fastener`. CalculiX set names keep signs (`+z` → P, `-z` → M): box sides used to share a set.
- **Material models** (`Material.models`: plasticity, orthotropic elasticity, hyperelasticity, anisotropic conductivity; `Material.solver_keywords`): an adapter writes those in `Capabilities.material_models` (`material_keywords` for keywords) and `Adapter.check` refuses the rest, only for studies that solve the model's physics. Plasticity is written by CalculiX (`*PLASTIC`, stepped static steps, PEEQ out) and Code_Aster (`VMIS_ISOT_TRAC` in `STAT_NON_LINE`), benchmarked in `tests/integration/test_plasticity.py`; the other models are refused everywhere so far. A study whose materials lack a needed property reports `incomplete_material` (`Project.problems`), so runs are refused before writing input.
- **Material data:** only `generic.toml` ships. The maintainer's full library is generated from `Materials_Hunt_List.xlsx` by `scripts/import_materials.py` into the user library (`puzzle.materials.user_library_path()`, outside the repo) and must never be committed. Tests set `PUZZLE_MATERIALS=""` (generics only) in `tests/conftest.py`; anything tests or examples use must be generic.
